# Harness Dock GPUI client

The shared Rust client uses GPUI Kit 0.9.0. It is a device owner's connection, execution-observation, discovery and maintenance panel. It calls the packaged `panel-cli.js` helper over bounded JSON stdin; the independently installed Daemon owns execution, native approval and recovery. The client does not host Provider processes or expose arbitrary model prompts.

App release `v0.1.3` uses this desktop frontend. macOS arm64 packaging targets macOS 15+. The desktop version comes from Cargo and is independent of the bundled Daemon `0.1.3`; the macOS bundle uses short version `0.1.3` and build `7`. The older Swift App v0.1.2 remains available for macOS 13+. Windows GUI compilation, tray, single instance, URL activation and real Daemon acceptance still require Windows validation; a common source tree alone does not establish support.

From the repository root, with Node, pnpm and a current stable Rust toolchain installed:

```sh
pnpm install --frozen-lockfile
pnpm check
pnpm panel:gpui:check
pnpm panel:gpui:build --output .local/gpui-candidate
```

The build creates an ad-hoc signed `.app`, ZIP and checksum, including the Node runtime, Daemon, dependency notices and offline `Contents/Resources/ConnectionHelp.html`. The help page is generated from the current device-user sections in canonical `apps/docs-site/src/content.json`; it needs no external styles, scripts or newly deployed website anchors. Cargo output goes to ignored `.local/gpui-build` (or `CARGO_TARGET_DIR`). Build output is never installed or published automatically. Open the packaged app; `cargo run` has no bundled helper. `Harness Dock.app/Contents/MacOS/HarnessDock --config /private/device/config.json` selects a specific configuration without reading or changing the normal selection preferences.

The normal client reads the existing `panel.json` selection. Closing a window hides the client; the tray can reopen it. Quitting removes the UI and tray while the Daemon continues. Installation and maintenance block normal UI exit until the helper finishes. A submitted fixed self-test has a private, durable request receipt; restart queries that identity instead of resubmitting. The receipt is not execution evidence. Model tests require explicit confirmation and may use native model quota. Environment diagnosis does not submit a model request.

On macOS, clicking the menu bar icon opens an AppKit menu. It shows the server state, any device attention, and shortcuts to Harness details. Open Main Window and Settings are explicit commands; Quit Interface leaves the Daemon running. The icon is a system-colored template. The menu uses the last device snapshot, labels older connection state when the window is hidden, and a click can trigger a refresh for the next opening. Windows retains the GPUI overview popup on left-click and the native command menu on right-click. Neither opens a model test.

The normal desktop client has one selected server binding. Overview offers **启动连接** when the service is stopped; a running service is stopped through the server row's **更多连接操作 → 停止连接…** menu. Stopping preserves the binding for a later start. The same menu's **移除服务器…** command is distinct: after confirmation, it asks the owner to stop only when idle, refuses pending receipts or unresolved work, unregisters its owned login service, confirms shutdown, then durably selects an empty binding. The old configuration, identity and history stay at their original paths. A new invitation or pairing is a separate explicit connection step with a new identity/state directory; native Harness selections and resource limits are retained. There are no parallel-add or profile-switch controls. Failures never start a second binding or automatically replay claims/tasks. Onboarding offers only a new invitation or server-provided pairing file; it does not browse or import previous device configurations. Helper-side selection fencing and a private OS-held operation lock cover simultaneous clients. Legacy locks require explicit checkpoint and host-restart verification before archival. Independent CLI installations remain outside this client's ownership.

GPUI Kit 0.9.0 is the presentation source of truth. `Theme::change` selects its registered stock Default Light or Default Dark theme; `src/theme.rs` only retains appearance selection and application layout measurements. There is no Dock palette, RGB token override, custom primary color or per-button background/text-color override. Component hover, disabled, loading, selection and focus states come from the library.

On macOS the shell follows the [shadcn/ui Dashboard layout](https://ui.shadcn.com/examples/dashboard) with a branded 208px sidebar, persistent Overview/Settings navigation and direct Harness entries. The content area fills its pane; it is not another rounded inset card around the page. GPUI Kit provides the sidebar, breadcrumbs and theme tokens. Page padding and the shared section-gap measurement are 28px, with an overview maximum content width of 1100px and a 520px connection form. The execution/usage columns stack below a 1040px window width. Ordinary `GroupBox` cards retain the library's default content inset; list groups explicitly remove wrapper padding so their `ListItem` rows own the inset once. Overview and Settings retain separate scroll positions. Server and Harness rows share a leading icon column and compact title/subtitle rhythm. Check packaged light/dark and minimum-size windows after shared layout changes.

The normal button variant is the library default Medium, matching the default Input. Primary identifies the current next step: initial connection, invitation confirmation, or starting an unavailable service. Secondary actions such as file selection, directory changes and optional model tests use Default with its visible border. Ghost serves refresh, help, compact icon utilities and the shared left-aligned `action_row` composition for usage details and connection tools; these rows include a trailing chevron or external-location arrow. Documentation links use Link. Stopping the connection and removing the server are `PopupMenuItem` actions behind the more button and open native confirmations. Do not assign variants by whether an action navigates or mutates: an essential navigation CTA still needs button affordance. Row height is application layout, while button padding, typography, radius and state colors remain library-owned.

Page structure uses GPUI Kit 0.9 public components throughout: `TitleBar`/`Toolbar` for the shell, `List`/`ListState`/`ListItem` for Harness lists, `Form`/`Field` for invitation and preference layouts, `DescriptionList` for test and technical facts, and `Accordion` for disclosure groups. Labels, copy actions, separators, empty states and scrollbars use `Label`, `Clipboard`, `Separator`, `Empty` and the stock scrollbar. Small `h_flex`/`v_flex` content slots hold branding, native artwork and business action groups; native window placement and bounded page/list geometry remain application responsibilities. There is no bespoke setting-row or disclosure component.

The full `Settings` component is not embedded inside the main window because version 0.9.0 always renders a second search sidebar and has no public body-only mode. Settings use the same library's `Form`/`Field` API inside `GroupBox`. Appearance uses `ButtonGroup`, login auto-connection uses `Switch`, and errors use `Alert`. The login switch is a future-login preference: it does not start, stop or restart the current owner, and it is not a maintenance confirmation. While unbound it remains visible but disabled with a reason. `panel/ui.rs` composes stock primitives; `panel/presentation.rs` centralizes connection and action projections, and `Panel` coordinates operations and receipts.

Connection onboarding uses two explicit stages in both appearances. From Overview, the entry screen explains that the remote server uses this computer's Harness while execution stays local. The invitation input and Primary “确认” action share a row. A separate “配对文件” row offers “选择文件” for a server-exported `device-pairing.json`; both routes lead to the same server/directory review. A local device `config.json` is not a pairing file: importing it returns the specific `device_config_is_not_pairing` error without changing its identity or state. Malformed JSON stays an invalid pairing error. Only “确认接入” establishes a connection. Editing or replacing input invalidates review. Advanced CA selection remains available. Status/log recovery remains available for uncertain outcomes without duplicate submission. Successful connection returns to Overview; the user then returns to the caller application for tasks, approvals and results. “接入说明” opens the packaged offline help rather than an unpublished website anchor. Native product artwork is embedded; the macOS menu bar uses a system-colored template.

Overview keeps server status and its service action together. Temporarily stopping the connection and removing its binding are separate actions with distinct consequences. Contextual guidance explains how to start the existing service, inspect a connection failure, or use the original installation's controls.

The connected overview reads `state.overview` from the protected local owner. Execution rows cover starts in the preceding 24 hours plus every nonterminal execution, with a distinct run ID for concurrent work. The snapshot contains at most 50 rows, prioritizing nonterminal work; counts and usage aggregate the entire matching scope. The UI initially shows 10 matching rows and offers more within that snapshot. Unknown outcomes remain unknown even after admission recovery. Remote server disconnection alone never changes a locally observed running execution to unknown. When the owner is unavailable, readable persisted records cannot establish that an old running execution remains live. Missing model/timestamp/duration evidence is not synthesized; retention migration timestamps are not completion evidence. These are execution facts, not business acceptance results.

Token totals are grouped by the named Codex/dsh adapters and cover executions **started in the preceding 24 hours** with valid per-execution usage reports. They include local model self-tests but exclude native work run independently of Dock. Cumulative native-session totals are not summed. Cached input is included in input, not added a second time; missing reporting is unavailable, not zero. Row truncation does not truncate totals. The usage detail view shows reporting coverage and separate input, cached input and output totals. No network speed or inferred token estimate is displayed.

An older independently running Daemon may not provide `overview`; the client shows unavailable data rather than an empty history. Updating only the App does not update that owner. Use the original managed-install upgrade path when idle and without unresolved work: it verifies the new bundle, asks the protected local owner to stop only if idle, preserves the binding/state/history and switches releases. A live owner's exclusive SQLite lock is never bypassed to fabricate a fallback snapshot. The old Swift v0.1.2 download is retained separately.

On macOS, the system draws the title bar and window controls. The sidebar switches directly between Overview, Harness details and Settings. Command-Comma and the status menu also open Settings. The 显示 menu offers the overview with Command-1 and refresh with Command-R. Refresh also appears in the overview header. Other platforms use the GPUI Kit title bar and toolbar. The connected overview does not repeat the sidebar's installation list. Click and keyboard confirmation use the same navigation callback.

Routine polling reads connection, execution and maintenance state without running native installation probes. The UI retains the last installation snapshot and reconciles fixed-test support against the current daemon. Startup, explicit refresh, connection selection and receipt verification refresh discovery. Pending dispatch receipts still query their original identity; this optimization never resubmits work. A failed state refresh marks installation and test summaries as awaiting refresh consistently in the tray and main window. A successful read after failure refreshes discovery rather than re-certifying the cached snapshot. While a window or tray is visible, ordinary execution/usage snapshots refresh about every 10 seconds; fixed self-tests or pending test receipts use 2 seconds. Open native dialogs and busy operations defer polling. Ordinary hidden-window polling pauses, while the independent Daemon continues recording. Codex usage is aggregated from the persisted execution result after that execution finishes, not from a live token-speed meter.

Keep local installation backups, selected configurations, runtime logs, screenshots and verification evidence in ignored `.local/`. Source compilation, packaged lifecycle, native model execution and Windows acceptance are separate evidence categories; see `apps/docs-site/README.md#verification`.

Harness details use a 720-point reading width and lead with the native Harness identity and factual installation status. Read-only model, reasoning and permission rules are grouped with always-visible native paths; optional model testing follows these facts. The “测试 <Harness>” action retains explicit quota/permission confirmation and never runs automatically. Native paths stay visible; receipt IDs are shown with optional test results. Settings groups appearance and login auto-connection under 常规, with technical information for configured devices and recovery controls only when needed. Connection diagnostics and Finder log-location actions live in Overview's 连接工具 section. Settings does not duplicate these tools, the server card or start/stop actions. Installation upgrades and rollback remain in the local maintenance CLI. Incomplete claims are resumed from the connection page; the optional previous-configuration chooser is not exposed. Legacy-lock and unresolved-execution recovery blocks remain available where required. Connection diagnosis leads with a conclusion and actionable failures, with a fixed check time and a stock Accordion for full details. Codex and dsh network checks have distinct names. An unavailable independent health probe or unperformed model test does not negate an accepted server connection; missing required evidence cannot produce an all-clear. Unknown checks are not shown as confirmed failures.


Device facts stay separate: server connectivity, local service lifetime, native installation detection and the last optional test result do not imply one another. Shared attention rules lead the main content and tray when work is active, a test receipt is pending, results are unresolved or legacy operations need review. Operation errors appear before the page body; logs open in Finder instead of expanding into the page. Overview describes a running-but-disconnected service without promising task reception. Offline persistent execution evidence remains visible rather than being treated as an empty task list.

Native confirmation and file-picker results are never silently dropped by polling. Polling pauses while a system dialog is open. An accepted decision waits for a current owner read, then revalidates the selected config, node and daemon, plus the relevant Harness or invitation review, before one dispatch. A busy or changed owner produces a visible explanation. A submitted or unconfirmed mutation is never put back in that queue. Confirmation buttons name the actual action. Theme choices expose pressed state, navigation uses native selected tree-item state, and Accordion owns disclosure state; assistive-technology behavior still requires packaged runtime verification.

Pairing-file preview returns a digest; confirmation sends that exact digest, and a changed file invalidates review. A persisted `connectionRecovery` claim reuses the original server, directory and CA in the same review screen, with “继续原接入” completing local setup without redeeming again. When the original outcome is unknown and no local recovery material exists, ending review requires explicit confirmation and a new administrator-verified invitation. A pending test whose owner has stopped can explicitly restore that service and query its original receipt; it does not submit the test again.

Troubleshooting separates unresolved execution from old operation locks. Admission recovery preserves unknown records and needs an explicit checkpoint and verified host restart before enabling new work. Legacy connection/installation locks have their own explicit checkpoint and restart-verified archival; archival does not reopen unresolved execution admission. Neither flow restarts the computer, erases history, cancels an unknown task, retries installation or resubmits work. Active work, pending receipts, stale state and concurrent operations keep recovery controls disabled.

Harness details read native models, model-specific reasoning choices and probe-session defaults through the protected local Daemon. Opening a detail page may inspect once when the supported owner is idle; normal polling only reads its cached snapshot. Re-read is explicit, and active tests/executions or unknown outcomes refuse inspection. The native adapters send no model prompt for this operation. The local response projects bounded metadata only, excluding native config/environment/credentials. Model labels and provider names are presentation metadata separate from opaque execution identities. Current native session defaults include local configuration overrides; they are not manufacturer defaults. Missing model/effort values remain unavailable, and an unexposed permission mode is described as native-managed rather than a read failure. No mode is inferred from ACPX fallback policy or installation status. Configured callers can still override task settings; this page never writes native settings. An unbound/stopped/older owner explains why model information is unavailable. App replacement alone does not update the independent owner.
