# macOS 设备面板

设备面板是设备持有人的轻量接入、状态与维护入口：把这台 Mac 上的原生 Harness 接到 Dock，供调用方产品选择并发起任务。执行由独立 Daemon 持有，任务、原生审批和结果回到调用方应用。业务授权与结果验收归应用，内部工具与原生权限归 Harness。

轻量菜单栏 App，使用系统 AppKit / SwiftUI，支持 macOS 13+、Apple Silicon。App 提供设备连接与维护界面，独立后台 Daemon 管理原生进程和执行记录，运行它们的这台 Mac 是执行设备；业务任务在提供邀请的调用方应用中发起。

App `v0.1.2` 支持 Codex 与实验性 dsh 适配。首页展示 Harness 数量和安装列表，点击条目进入详情，按需执行对应固定回显。App 与独立 SDK `sdk-v0.1.0` 分别发行；原生 Harness 仍由设备用户安装、登录和管理。

## 安装与接入

设备用户直接安装 App，不需要 Git、Node、pnpm、终端命令或 JSON 文件。日常操作请先看 [App 使用指南](https://hutian-ai.github.io/harness-dock/app/)，按菜单栏打开、查看状态、测试和维护的流程使用；下文保留安装细节与维护者说明。

以下步骤面向已发布 App `v0.1.2`。先取得服务管理员提供的邀请；没有邀请的应用开发者可从 [SDK 首次任务](https://hutian-ai.github.io/harness-dock/sdk/#first-task)开始，管理员先[部署服务](https://hutian-ai.github.io/harness-dock/server/)并生成邀请。

1. 下载 [v0.1.2 Developer Alpha 客户端（macOS arm64 ZIP）](https://github.com/hutian-ai/harness-dock/releases/download/v0.1.2/harness-dock-panel-0.1.2-darwin-arm64.zip)；[版本说明](https://github.com/hutian-ai/harness-dock/releases/tag/v0.1.2)列出已知限制。
2. 解压并将 `Harness Dock.app` 拖入“应用程序”目录（或 `~/Applications`），双击打开。
3. 打开管理员提供的邀请链接，在客户端核对服务器并点击“连接这台 Mac”；也可粘贴邀请链接。已有设备优先使用原连接。
4. 实际执行前，在这台 Mac 安装并登录原生 Codex，或单独安装、配置实验适配的 dsh；无需先完成本机回显才能接入服务。
5. 需要核验时点击首页 Harness 条目，在详情中使用“运行诊断”检查环境，或点击“测试 Codex”/“测试 dsh”核对一次模型回显。查看通过、失败或结果待核对以及最近检查时间；只有进入模型执行才使用额度。
6. 回到接入的应用发起任务；原生审批和业务结果仍在应用中处理。

支持 macOS 13+、Apple Silicon。App 已随带运行时和 Daemon；仍为 Developer Alpha，仅有 ad-hoc 签名，尚未完成 Developer ID 签名与公证，macOS 可能阻止首次打开。遇到限制可[联系维护者](https://github.com/hutian-ai/harness-dock/issues)，提供脱敏后的系统版本和错误提示。源码构建部分面向维护者。

## 接入后的使用

App `v0.1.2` 首页突出已检测到的 Harness 数量和列表，独立显示服务连接，并提供“设置与维护”入口，不常驻展示任务统计。点击 Harness 条目进入详情，查看安装信息、按需固定回显、分环境历史及诊断；“设置与维护”是可返回首页的独立页面，收纳本地日志、版本信息、登录自启、停止、更新和回滚。首次邀请接入无需先选择或验证 Harness。已有安装需要新版后台能力时，按下方步骤显式更新后台；旧后台未报告对应能力时不会启用该测试。

面板与菜单栏使用和 App 图标同源的标识，菜单栏为适配小尺寸的单色 template；界面采用系统字体、中性按钮和随系统切换的浅深色外观。保留 Logo 原色，安装与状态文字使用中性色，连接或回显通过仅以小面积柔和绿色图标标示。

1. **查看本机 Harness**：首页核对安装数量、各条目的安装与最近回显状态，再确认服务连接。数量只统计已发现的安装，未发现、禁用或待确认条目不计入；检测未完成不显示为零，刷新失败保留上次结果并标明。安装发现或连接成功不等于模型、工具或业务应用已验收。
2. **回到应用使用**：正常情况下，在调用方应用发任务、看进度、处理原生审批和接收结果。面板不提供任务业务面板或审批管理。
3. **按需检查 Harness**：点击首页 Harness 条目，查看版本和来源，按需进行条目支持的固定回显，并查看原测试记录；详情只提供一个返回入口。Codex 使用原生确认的只读模式；dsh 实验固定回显沿用原生权限配置，不提供只读保证。出现工具活动或额外审批不会判定通过。测试会使用模型额度；诊断不发送模型请求。安装未发现、已禁用或后台未提供对应能力时按提示诊断；设备忙或有待核对执行时先处理原执行。
4. **需要时维护**：打开“设置与维护”独立页面查看版本、本地日志和安装与连接诊断，更改登录自启、停止后台、更新或回滚。后台拥有者仍会检查活动及 unknown 执行；面板不提供一键解锁未确认结果。

本机自检属于设备维护，不借用应用身份、不覆盖已连接应用的回调，也不改变设备归属。高级的应用端到端验收仍使用 SDK 两轮回显与可选原生审批测试：每台设备只有一个应用拥有者，每个应用身份只有一个活动连接。已有应用连接时，复用它的 SDK 连接；CLI 只在该应用身份没有其他活动连接时使用。独立实验使用隔离 server/设备身份。

Harness 列表按后台返回条目展示名称和安装状态，详情中可查看版本、发现来源、可执行文件与原生 Home。当前只提供已实现的 Codex/dsh 适配，每类使用后台选定的安装与 home，不枚举任意 home 或帐号。可用测试类型和额外验收命令来自后台能力元数据，未知或未支持的条目不会因此获得执行能力。历史按环境隔离，旧环境的结果不会作为另一环境的通过证明。任一 Harness 的测试运行中或启动收据待确认时，可只读查看其他 Harness 详情，但不改变原测试归属，也不能另启测试、停止或维护后台；只查询原 Harness 与测试编号，不自动重新发送模型请求。

“结果待核对”表示 `unknown` 执行缺少确定完成证据；应用任务由原调用方按原 runId 查询，本机自检由面板查询原测试编号。它不是原生权限审批；不要清空状态或重发请求来消除提示。设备有活动或 unknown 执行时，维护操作被阻止并显示对应原因，首页不常驻展示执行数量。

右上角收起按钮只隐藏弹层，菜单栏图标和 App 进程继续保留；“设置与维护”中的“退出 LaunchApp”结束界面应用并移除菜单栏图标，独立 Daemon 继续运行；尚未接入时可在“设置与维护”中退出 App。“停止后台”才通过本地拥有者检查空闲后停止后台。安装或维护写操作进行中仍可收起，App 与 helper 继续处理；真正退出被禁用，避免中断写操作。状态暂不可用时保留已读信息，并先刷新或诊断，不把陈旧状态当作当前在线证明。安装已保存身份但尚未完成时，可从原配置继续安装，无需领取另一份邀请。

## 维护者：构建客户端

以下命令由生成候选包的维护者执行，设备用户不需要构建。

在已安装依赖的仓库根目录执行（需要 Xcode 命令行工具）：

```sh
pnpm panel:build
# 也可复用同平台、已验证的运行包；输出目录必须不存在：
pnpm panel:build --bundles .local/bundles/candidate --output .local/panel/candidate
```

产物为 `Harness Dock.app`、ZIP、摘要与安装说明，全部位于 ignored 的 `.local/`。App 随带 Daemon、Node、依赖、补丁和许可。默认使用当前 Node 及其安装根目录的 LICENSE；可用 `--node /absolute/node --node-license /absolute/LICENSE` 显式选择。运行时必须为 macOS arm64、Node 22.19+，且只链接系统动态库；拒绝依赖外部 Homebrew 动态库的构建。构建只进行本地 ad-hoc 签名，不等于 Developer ID 签名或公证；公开发行还需核对源码来源、验证范围和 Release 资产。

用户将 App 移入 `~/Applications` 后打开，无需安装 Git、pnpm 或 Node。所选原生 Codex/dsh 由用户自己安装、登录和授权；App 不另行安装 dsh 或复制原生认证。接入向导不会调用模型，也不建立第二条设备身份连接。

## 更新本机 App 与后台

替换 `Harness Dock.app` 只更新面板及其随包资源，已经安装的后台仍运行其固定 release。旧后台需要新包提供的 dsh 实验适配或后台修复时，按以下步骤显式更新：

1. 先确认已有设备没有活动或 unknown 执行；有待核对任务时，回到原调用方按原身份处理，不通过清理状态绕过维护限制。
2. 退出当前 App：旧 v0.1.1 使用底部“退出面板”，v0.1.2 使用“设置与维护”→“退出 LaunchApp”。以同平台的新版 App 替换本机 App，再打开原配置。退出 App 会保留后台；设备身份、私有配置、状态与工作目录不随 App 替换而重新创建。
3. 在“设置与维护”中点击“更新后台…”，核对后确认“更新至此应用附带版本”。入口仅在此应用自管的后台与随包版本不同时显示。helper 校验随包运行包，并由后台拥有者通过受保护 socket 再次检查空闲、升级和读回状态。不要手动覆盖运行中的 release 或按保存 PID 停机。
4. 核对已安装后台 release、设备身份与连接状态。升级结果未确认时只读查询状态和日志，不自动重试升级或重发执行。

版本一致时显示“后台与此应用附带版本一致。”；可更新时显示“已安装后台与此应用附带版本不同，可显式更新。”。这些提示仅比较清单元数据，不表示随包版本号更高，也不替代实际更新时的运行包完整校验。

dsh 任务仍由应用 SDK 以 `provider: 'dsh'` 发起，模型值从设备 inventory 原样选择。“测试 dsh”只证明本次固定回显，不保证只读，也不验证工具、业务授权或独立设备。公开 App 与本机构建候选的产物来源和验证记录分别保存。

## 所有权与本地接口

公开客户端由 `.github/workflows/release.yml` 从 `v<package.json 版本>` 标签的干净源码构建。工作流检查原生平台、源码与运行包提交一致性，运行确定性检查、源码冒烟和离线分发验收；随后只上传客户端 ZIP、SHA256SUMS、README.txt 与 release.json，下载读回逐字节核对后才公开 Developer Alpha Release。不会上传本机 `.local/`、凭据、日志、验证截图或发布 npm 包。维护者先确认主分支 CI，再创建发布标签；发布说明维护在 `.github/release-notes/<标签>.md`。

- `NSStatusItem` 打开 400px 宽的原生弹层。首页按实际内容收紧高度，详情、设置和接入流程保留查看空间；长内容超过高度上限时滚动。参考 Magpie 的紧凑菜单栏布局与逐项操作方式；本实现不复用其代码、品牌或模型网关。
- App 以 stdin JSON 启动随包的 `daemon/dist/panel-cli.js`。没有额外 HTTP 监听端口；本机测试经原有受保护 Unix socket 请求 Daemon 启动固定自检，不接受任意 prompt、工具或权限决定，不建立第二条设备/应用连接。
- helper 复用 Daemon 的 `setupDevice`、`manageInstallation`、`startInstalled`、`stopIdleDaemon`、`deviceDiagnostics`；状态和停机经过原有受保护 Unix socket，绝不使用保存 PID 发信号。
- 主要入口是服务器生成的 HTTPS 邀请链接：网页通过 `harness-dock://connect?invite=…` 唤起 App；已运行实例接收链接并置前。客户端预览只显示服务器，用户点击“连接这台 Mac”后才领取一次短期邀请、持久化私有配置并复用 setup。粘贴链接提供备用入口，网络请求不跟随重定向、不自动重试，TLS 始终校验。
- 旧 JSON 邀请在高级设置导入，允许用户选择从下载目录取得的普通 JSON 文件；有界读取并验证身份、token 和 TLS 地址，不改变原文件权限，不打印 token。持久化使用原有 0700 设备目录与 0600 配置。导入不等于服务端已经授权或加载配置，连接状态以拥有者读回为准。
- 本机检测仅检查已选配置、默认设备配置和本产品自己的用户 LaunchAgent（最多 16 项），不递归搜索 home 或实验目录。支持旧 `dev.harness-dock.device.plist` 和现有 `org.harness-dock.device.*.plist`。设备选择列表只展示服务与连接状态，不展示凭据。
- 首次接入通过“打开邀请链接 → 确认服务器 → 连接”完成；旧 `device-pairing.json` 导入保留在高级设置。没有邀请时提供获取说明与可复制申请，服务端注册/授权仍由管理员完成，不冒充自动签发。工作目录自动使用 `~/harness-work`，私有 CA、目录修改和旧配置文件导入统一收进高级设置。
- 默认设备配置为 `~/.harness-dock/.local/device/config.json`；面板只在 `~/.harness-dock/.local/panel.json` 保存所选配置的路径。已有安装可以自动检测或导入 config；源码设备可显式使用此应用管理…。自定义目录的既有版本化安装只观察和诊断，继续通过原入口维护。
- 迁移旧源码设备时先验证 App 内的运行包，再让拥有者原子检查空闲并停机。只退役与该配置精确匹配的旧 `dev.harness-dock.device` 用户服务，将原 plist 与原自启偏好保存在配置目录的 `retired-autostart/`，保留配置、状态路径、执行身份和工作文件。随后安装随包 Daemon 并按原偏好注册新自启。失败后不重放任务，不按 PID 强杀；重新读回状态。
- 自启显式开启，使用当前用户 LaunchAgent。右上角收起按钮只隐藏弹层；“退出 LaunchApp”结束 App 与菜单栏图标，两者都不停止 Daemon。退出 App 后活动执行、审批和恢复仍归 Daemon 与原调用方。
- 停机、自启更改、升级与回滚由拥有者再次检查活动 / unknown 执行。失败后读回状态，不重试写操作、不重放任何任务。
- 安装和维护显示等待说明，面板不会因固定 UI 超时而中断写操作；完成与否以 helper 返回和拥有者状态读回为准。只读检查有独立等待上限。
- 随包 Node 安装到不可变 Daemon release 内；移动 App 不影响已安装设备。更新面板后可在“设置与维护”中明确点击“更新后台…”并确认“更新至此应用附带版本”，回滚也必须明确点击。两者不撤销数据库变化或外部效果。
- 日志仅手动打开本地尾部，不自动上传。“诊断”不发送模型请求；点击所选 Harness 的测试按钮才提交固定合成内容。安装发现、服务器连接、本机模型执行、具体桌面与工具能力分别展示和验收。
- Daemon 先按 Harness 和测试编号持久化收据，再通过现有 DeviceHost → ACPX → 对应原生适配器执行固定回显。Codex 只使用原生探测确认的只读模式；dsh 沿用原生权限配置，不提供只读保证。两者都拒绝自检中的额外审批，观察到工具活动不会判定通过；不重绑定应用回调，也没有平行执行后端。
- 面板启动测试后只读轮询原任务。相同最新测试编号返回原状态，响应丢失、关闭面板和重新打开均不自动重发。后台重启时未完成自检为 unknown；保存记录仍由原 Daemon/执行状态规则处理，缺少完成证据不等于失败后可安全重试。

## 验证

`pnpm check` 覆盖共享安装、导入/身份冲突、敏感值投影、受保护停机、运行时迁移以及固定自检的控制边界。自检测试包括：仅接受已支持的 Harness 和测试 UUID、按 Harness 隔离历史与收据、持久化先于派发、重复/丢失收据不重派、后台重启转 unknown、持久化故障不报告成功、回调隔离、Codex 原生只读模式与 dsh 固定回显的验收条件。`pnpm panel:build` 验证原生编译、产物完整性与本地签名。实际 GUI、首次设备接入、旧设备迁移、自启、移动 App、升级/回滚需在目标 Mac 独立验收；本地产物构建不代表真实 Harness、签名公证或公开发行已经完成。

开发验收可指定独立配置打开应用：

```sh
open -n ".local/panel/candidate/Harness Dock.app" --args --config "$PWD/.local/panel-test/device/config.json"
```

原始截图、日志、设备标识及配对文件留在 `.local/`。

dsh 的维护者验收使用 `pnpm accept:dsh`，需要本机原生 dsh 登录与模型额度。六类本机 fixture 场景包括 MCP 成功/错误、调用方与原生项目 skills 共存、原生审批允许/拒绝/取消后旧决定失效；允许用例还核对一次性授权作用域。fixture 仅为测试原生子进程选择 read-only，不修改用户 settings 或已安装后台。MCP 错误在原生投影为 failed 时，送达状态保守保持 unknown。该本机 SDK / Server / DeviceHost 证据不替代独立后台进程、目标 Mac 首装升级或发行包验收，原始输入、回调和结果留在 ignored `.local/`。

## 邀请链接验收

服务端 `invite` 为已登记、已加载的设备生成默认 15 分钟、最长 1 小时的签名领取链接。长期设备凭据不放在链接中；`#` 片段不随网页请求发送。网页与客户端唤起参考 Magpie 的 Add to magpie 交互（https://usemagpie.ai/docs/import），没有复制代码、品牌或模型网关。确认前仅本地解析；确认后通过 HTTPS 领取一次，服务端独占并持久化消费记录，原有任务/审批/原生权限边界不变。

验证包括：邀请网页与深层链接唤起、已运行实例、未安装说明和粘贴备用入口、过期/篡改/重复/并发领取、重启防重放、身份冲突、网络响应未确认、私有 CA，以及使用隔离配置的真实 Daemon 连接。截图、测试邀请与部署证据留在 `.local/`。
