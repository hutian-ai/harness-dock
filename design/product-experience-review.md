# 界舟：产品、交互、视觉与实现整体评审

> Review snapshot: the findings below describe the implementation before desktop candidate `0.1.3-preview.1`. That candidate separates login preference from current service lifetime, preserves unknown activity, moves current connection actions to Overview, separates removal from stop, brings old-configuration startup into the same flow, simplifies settings and optional tests, and bundles device-facing help. A shared connection/activity projection replaces the duplicated primary state interpretation. The helper request channel remains serialized; navigation and theme changes remain available during reads, while state-dependent actions retain their freshness guards. Native validation evidence belongs in ignored `.local/`, not this tracked review.

评审日期：2026-11-06。依据：本轮用户历史反馈、当前 GPUI 客户端实机页面、面板与管理 helper 源码、SDK / Server / Daemon 契约，以及官方参考。本文是设计和整改依据，**不表示下面的改动已经实现或验收**。

## 1. 总体结论

当前客户端不能算产品完成。反复调整间距没有解决根本问题：界面按后台提供的操作组织，而不是按设备持有人的目的组织。与此同时，状态解释散落在多个页面中；组件库已接入，但页面的主次、密度、操作含义和交付核验没有形成稳定规则。

不是整个工程都应该重写。设备独立执行、原生 Harness 所有权、原结果查询、邀请领取防重、受保护本地管理和操作前身份复核是正确基础。需要重新设计的是：用户如何理解并使用这些能力，以及 UI 如何从真实状态派生行动。

### 产品的一句话定义

**界舟让产品使用指定电脑上的原生 Harness，并管理跨设备执行的连接与生命周期。**

桌面端的一句话定义：**把这台电脑接入远端服务器，查看本机 Harness 和连接状态，处理需要设备持有人介入的问题。**

它不承担业务任务编排、对话、IDE、原生插件管理或结果验收。用户不应为了连接设备，先学会 Daemon、ACP、回执、操作锁和版本目录。

### 三类用户及各自的完成标准

| 使用者 | 目的 | 完成依据 | 交接 |
| --- | --- | --- | --- |
| 应用 / Agent 开发者 | 从自己的产品调用指定设备上的 Harness | 获授权设备执行真实任务，取得确认终态，接回并验收结果 | 使用 SDK，保留执行身份与结果；审批留在调用方 |
| 服务管理员 | 建立可信连接、授权应用和设备 | 服务器实际加载正确配置，目标网络与凭据验证成功 | 给应用提供应用凭据；给设备持有人提供邀请 |
| 设备持有人 | 提供这台电脑的原生执行环境 | 接入预期服务器，知道本机安装情况和需要处理的问题 | 回到提供邀请的应用使用；客户端可收起 |

“已连接”“已安装”“一次响应测试通过”“业务任务成功”是四种证据。界面可以简洁，不能把它们合并成未经证实的“全部就绪”。

## 2. 当前必须解决的问题

优先级：P1 是动作语义、状态可信性或链路阻塞；P2 是理解成本、视觉一致性或交付质量。以下以当前代码为准，不把历史截图中已经删除的日志弹窗、版本维护横条等继续列为现存缺陷。

| 优先级 | 问题与用户影响 | 当前依据 | 应达到的结果 |
| --- | --- | --- | --- |
| P1 | “登录后自动连接”关闭时停止当前服务；开启时可能先停再启动。用户修改未来偏好，却改变当前运行。 | `panel/view/settings.rs` 的偏好确认；`installation.ts` 的 `autostart` 分支；`autostart.ts` 的 `disable` 实际执行 bootout 并删除注册文件。 | 未来登录偏好与当前启停分离。断开所需的完整注销能力仍保留；不能直接修改底层 `disable` 的含义。 |
| P1 | 后台不在线时返回活动数和未核对数均为 0，面板可能展示可断开 / 可维护，实际执行时又因历史任务被拒绝。 | `panel-management.ts:169–199`；`process-management.ts:23–40`。后者读取持久化记录并拒绝未核对执行。 | helper 返回有来源的离线执行摘要。无法读取是“无法确认”，不能默认为空闲。UI 不直接读取数据库。 |
| P1 | “恢复以前的连接”只保存选中的配置。后台已停止时，恢复后还要去设置找启动。 | `recovery_choices.rs` 的 `select-connection`；`panel-management.ts` 该分支；`panel.rs` 选择后导航。 | 选择旧身份后在当前流程提供明确连接动作，并读回实际状态。未核对任务可先启动原拥有者用于查询，但不能顺便重发任务。 |
| P1 | “断开”实际上结束客户端当前绑定，而“停止服务”保留绑定。两个分散入口让用户难以预判后果。 | `panel-management.ts` 的 `disconnect` / `stop`；概览与设置动作。 | 当前启停与解除绑定成为两个明确意图，集中在连接上下文。正常暂停保留服务器；移除连接才清空当前选择。 |
| P1 | 邀请 / 配对读取错误让用户去“设置查看技术记录”，而未接入设置隐藏技术信息，也没有该名称的入口。 | `panel.rs:835–840`；`settings.rs:404–423`。 | 错误旁直接给实际存在的下一步；无日志时不承诺日志存在。字段错误留在字段，接入结果未知进入专门核对态。 |
| P2 | 设备用户点击“接入说明”，进入首屏为 Docker / CLI 命令的管理员页面。 | `connect.rs` 链接 `/pairing/`；canonical pairing 页面明确面向服务管理员。 | 链接到对应客户端版本的设备使用步骤。页面内直接说明邀请来自部署服务器的人；管理员指南只作次级交接。 |
| P2 | 安装、登录、协议可用、模型测试混在 Harness 页面；概览长期显示“尚未测试”，容易让可选测试像必做任务。 | `home.rs::harness_rows`、`provider.rs::provider_page`、`panel.rs::test_label`。 | 列表表达安装证据与当前异常；未做可选测试不成为缺陷标签。详情中测试有明确目的、额度提示和证据范围。 |
| P2 | 接入成功后的产品交接弱。用户知道服务器连上了，却仍不知道去哪里发任务。 | 接入成功返回概览；界面聚焦安装与测试，canonical quickstart 才解释回调用方。 | 首次成功给一句“回到提供邀请的应用发起任务”。没有可信应用链接时不伪造“打开应用”按钮。 |
| P2 | 绑定、服务、联网、执行占用、测试的状态，在概览、设置、详情和托盘各自拼接。缺字段还常被当 false。 | `Panel` 持有 raw JSON；`status_label`、`settings_service`、详情、托盘分别判断。 | 管理数据在边界解析，保留未知；集中派生用户状态、原因与可用动作，所有入口复用。 |
| P2 | 普通读取和用户修改共用 `busy`；轮询或安装检测可能令控件短暂不可用，表现像界面迟钝。 | `panel.rs::request` / `tick`，视图 `.disabled(self.busy)`；helper 读取超时。 | 读取保留最后快照并显示更新中；只锁住依赖该结果的动作。修改仍串行、重验身份，不自动重放。 |
| P2 | 同版本名下，公开 Swift 客户端、当前 GPUI 候选与独立后台并存。帮助文案和检查覆盖容易对不上实际产物。 | `apps/gpui-panel/README.md`、docs distribution / app 页面、打包脚本。 | 明确实际前端 / 构建来源 / 系统要求；设备帮助匹配所用客户端。公开下载说明不得被未发布候选行为覆盖。 |
| P2 | `pnpm check` 的 native panel 检查是 Swift；GPUI 是单独命令。整条检查通过不能证明当前 UI 通过。 | `package.json`、`scripts/check-panel.ts`、`scripts/check-gpui-panel.ts`。 | 对 GPUI 交付明确执行其检查和实际候选构建。源码检查、当前安装产物、视觉验收分别记录。 |

## 3. 不再变动的产品结构

保留窄侧栏和主窗口，不再在侧栏、底部按钮、菜单入口、独立设置窗口之间反复切换。

```text
界舟 / Harness Dock
├─ 概览
│  ├─ 当前连接与需要处理的情况
│  ├─ 本机 Harness 列表
│  ├─ 接入服务器（次级流程）
│  └─ Codex / DeepSeek Harness（对象详情）
└─ 设置
   ├─ 外观与登录偏好
   └─ 诊断、日志位置、按需技术信息
```

- 侧栏只放真实的一级目的，不加“设备管理”空分组，不为了填满留白而新增页。
- 接入和 Harness 详情属于概览，用同一个面包屑返回；设置是一级页，不再加页面内返回按钮。
- macOS 系统标题栏和窗口控制保留，原生菜单与 Command-Comma 作为快捷入口，不能替代可见的设置导航。
- 菜单栏是状态与快捷进入主窗口，不做第二套设置和维护流程。

### 当前连接只表达一个下一步

| 状态 | 用户看到什么 | 主要动作 | 禁止的推断 |
| --- | --- | --- | --- |
| 尚未接入 | 这台电脑尚未连接远端服务器 | 接入服务器 | 不显示连接失败，不要求先做模型测试 |
| 正在读状态 | 上次快照 + 正在更新 | 普通导航可用 | 不把暂时缺数据显示成未配置 |
| 已绑定、服务停止 | 原服务器 + 连接服务已停止 | 启动连接 | 不要求新邀请 |
| 正在连接 | 原服务器 + 正在连接 | 正常等待；超时后诊断 | 不提前声称在线 |
| 连接失败 | 原服务器 + 可理解的原因 | 检查连接 | 不默认建议解除绑定 |
| 已连接且无异常 | 服务器 + 已连接 | 无强制主要动作 | 不声称所有 Harness / 工具可执行 |
| 任务执行中 | 原连接 + 执行中的简短提示 | 去原应用查看（有真实入口时） | 不提供会中断拥有者的维护操作 |
| 结果未知 | 原连接 + 原结果需要核对 | 查询原结果 / 按原因恢复拥有者 | 不把 unknown 当失败、取消或可重试 |

“暂停连接”若用于产品文案，必须明确其实现是空闲时停止本机连接服务，而不是暂停运行中的任务。最终动作命名应在实现语义确定后统一，不能先改名再让副作用迁就名称。

### 四种恢复分开处理

1. **已有配置重新使用：** 找到原服务器和身份 → 用户选择 → 如需要则启动原服务 → 读回状态。
2. **邀请已经领取但本机安装未完成：** 继续原接入，不再次兑换邀请。
3. **接入请求结果未知：** 先核对，不能展示另一个可重复提交的确认按钮。
4. **原任务结束证据不足：** 保留原记录，按后台提供的恢复能力处理；技术检查点和重启证据只在此异常上下文出现。

旧版操作锁归档是维护特例，不属于普通用户的“恢复连接”。普通接入页不罗列这一能力。

## 4. 各页的最终职责与布局

### 概览

回答三个问题：接到哪里、发现哪些 Harness、现在是否需要我操作。

- 连接区以服务器身份和状态为主体。未接入时显示接入动作；已停止时直接启动，不能让用户去设置完成连接。
- 解除当前绑定放在连接区次级操作中；确认文字说清停止服务、关闭其自启、保留原身份和历史。不要让日常暂停与换服务器混为一谈。
- Harness 列表继续使用 Kit List，保持品牌图标、名称、副信息、进入箭头的固定列。安装未知 / 未找到 / 已停用有文字，不用亮绿标签装饰正常状态。
- 有历史测试时可展示最近结果；从未测试时只展示版本与实验性说明，不长期显示“尚未测试”催促操作。
- 活动和异常只在发生时出现一条准确提示；不新增空的任务仪表盘或执行历史中心。

### 接入服务器

这个页面首先是一项短任务，不应像管理后台的一组设置卡。

- 固定标题“接入服务器”，保留用户确认过的说明：“让远端服务器使用这台电脑上的 Harness，任务在本机执行。”
- 不再把整个邀请与文件表单套进一张大卡片。主输入直接落在页面内容网格上：邀请链接标签、输入与“确认”、来源说明与小号帮助。
- “配对文件 / 选择文件”是一条紧凑的次选方式，不再使用两行说明把它做成第二个主功能。
- “使用以前的连接”是更低权重入口；只有展开后才解释查找记录 / 选择备份。配对文件与旧配置文件不同，不用一个模糊文件按钮偷偷识别两种身份操作。
- 输入“确认”仅读取信息，下一屏的最终动作必须准确表达建立连接。网页唤起和文件导入进入同一核对流程。
- 核对时展示实际服务器、工作目录及原生权限归属。工作目录是执行起点，不宣称为安全沙箱。自定义 CA 仅在高级选项出现。
- 无效链接就地提示；领取结果未知替换当前表单为核对态，不在失效输入上方堆新的竞争操作。

### Harness 详情

- 顶部身份区：清晰 logo、名称、安装证据和版本。未发现时提供实际安装 / 登录指引与重新检测，不让用户猜“怎么变成可用”。
- 连接状态属于整台设备。详情可以给必要前置条件，但不复制一张完整的“接入服务器”广告卡抢占内容。
- “响应测试”是可选排障能力：说明会发送一条简短请求并使用额度，按钮为次级样式；结果、时间和下一步就地呈现。
- 已安装不暗示已登录；没有验证就明确保留未知。Codex 只读测试与 dsh 原生权限的区别放在实际发起前的确认中。
- 路径、原生 home、测试 ID 收在一层技术信息中；复制动作可见，长值有完整查看方式。日志去 Finder，不展开整页 JSON。

### 设置

- 常规偏好只包括当前真正存在的外观和登录自动连接。未接入时保留自动连接的真实控件与简短不可用原因，避免“待接入”假状态，也避免设置结构随绑定凭空消失。
- 自启解耦前，不把当前副作用包装成无害偏好开关。实现与文案必须一起整改。
- 当前连接启停归概览。设置的“诊断”面向排查，说明“不发送模型请求”；结果回答哪一项有问题、下一步是什么。
- “日志位置”直接打开 Finder / 平台文件管理器。没有日志时给真实结果，不弹无限长日志视图。
- 程序路径、版本来源、配置位置放一层技术信息；版本切换 / 回滚留给维护 CLI，普通页不陈列内部发布操作。
- 恢复未知执行或旧操作锁，只在相关异常存在时出现，并先给一句问题和影响，再按需展示技术步骤。

### 菜单栏

复用同一状态映射；连接状态、Harness 快捷入口、打开主窗口、设置、退出界面。保留“退出界面不等于停止服务”的真实行为。旧快照必须标注，点击菜单不能自动发起模型测试、恢复或重新接入。

## 5. 视觉规范：少做层级，不是少做间距

当前实机问题是“系统标题栏 → inset 内容外框 → 面包屑栏 → 页面标题 → 内容卡 → 字段”层层加重。相同 14px 字号反复用于标题、导航、动作、状态，再用越来越多盒子区分。用户感到松散，不是把所有 gap 减少就能修复。

### 固定规则

| 内容 | 规则 |
| --- | --- |
| 应用壳 | 保留窄侧栏、统一内容 header。主画布承担分区，不再给每页增加完整页外框和每项内容外框。最多一层有意义的分组边界。 |
| 默认尺寸 | 以当前约 800pt 宽的桌面工具为尺度，不为宽屏后台填充指标。窄窗保留阅读与动作，不横向挤压。 |
| 侧栏 | 约 176pt。品牌和副标题紧凑一组；概览 / 设置为两项稳定导航。空白可保留，不放重复状态与版本。 |
| 横向网格 | 内容左边距 24pt，分组内 16pt；带图标行统一 36pt 图标槽、12pt 间隔。页面标题、表单和区块左边界一致。 |
| 纵向节奏 | 区块间 24pt，组标题到内容 12pt，字段标签到控件 8pt，控件到帮助 6–8pt。每段间距只由一个父层拥有。 |
| 主副标题 | 列表沿用已修正的 18 / 16pt 行高、2pt gap。辅助信息不与主标题争同一字重。不要为了统一而重新放大这组间距。 |
| 字体 | 页面标题约 20pt / semibold，区块与行标题 14pt，辅助信息 12pt。普通状态与说明使用 normal；路径才用等宽。 |
| 按钮 | 用 Kit Default / Primary / Ghost 变体，默认与 Input 同高。一个情境最多一个强主要动作；按钮内容宽度自然，不拉伸成横条。 |
| 次级帮助 | 12pt，靠近对应字段。帮助链接不能与主按钮同权重；无障碍名称需要描述目标。 |
| 状态 | 短文字配小图标即可。颜色辅助表达，不取代文字，不用 Tag 模拟禁用按钮或满宽进度条。 |
| 分隔线 | 只分开同组同级行；起点统一对齐文本列或分组内边界，不随页面临时决定，最后一行无线。 |
| 主题 | 使用锁定的 GPUI Kit 浅深色 token 和控件状态。品牌绿只来自品牌资产；不另写一套按钮背景和文字颜色。 |
| 滚动 | 页面级单一主要滚动区。日志不嵌套滚动；设置切换保留自身位置。无实际溢出时不常驻滚动条。 |

GPUI Kit 已经被使用，问题不是“完全没用组件”。但把 GroupBox、Accordion、Form 拼到一起，也不自动构成好设计。库负责控件状态和基础样式，产品必须负责哪个信息该出现、出现在哪、占多少空间。

### 成熟参考与明确取舍

- [Tailscale 的客户端偏好](https://tailscale.com/docs/features/client/manage-preferences)：借鉴小型驻留客户端与管理端职责分离。设备用户管理本机连接，不被迫进入服务端管理操作。
- [Docker Desktop](https://docs.docker.com/desktop/use-desktop/)：借鉴对象列表进入详情、稳定的设置与排查入口。不复制它多资源、多模块的导航规模。
- [shadcn Sidebar blocks](https://ui.shadcn.com/blocks/sidebar)：借鉴侧栏、内容 header、面包屑的统一对齐。不要复制演示中的统计卡、空模块和为 Web 后台设计的大面积容器。

这些是结构参考；实际界面仍由 GPUI Kit 构成。不能以“像某个后台”代替适合设备客户端的判断。

## 6. 实现整理：保留安全内核，收敛展示层

### 必须保留

- UI 通过打包 helper 管理独立 Daemon，不运行 Provider 进程，不绕过原生认证或权限。
- 受保护本地 socket、config / node / daemon 身份复核、单服务器选择隔离、空闲维护检查。
- 邀请领取未知不重复领取；任务结果未知不重发 prompt、工具或审批；固定测试保留原收据并查询原结果。
- 程序回滚不承诺撤销已经发生的业务效果。断开不删除原身份、会话、历史与用户文件。

### 最小必要抽象

1. **管理快照。** 在 helper → Rust 边界解析明确字段，缺失与错误保留 Unknown；实时与离线持久化证据携带来源。无需把协议改成 UI 业务类型。
2. **状态派生。** 分别建模绑定、服务运行、服务器连通、执行占用、安装检测、测试结果；集中生成展示文案、主动作与不可用原因。不要做一个覆盖所有组合的巨大枚举。
3. **操作协调。** 读取与修改分开；修改保持串行与既有重验，轮询不反复冻结整页。操作提交和结果未知不能被普通读刷新清掉。
4. **有限的页面组合。** 仅统一页面 header、分组列表、设置 Form、状态与动作区域的布局策略。内部继续使用 Kit 组件，不新增通用设计框架或组件市场。
5. **按状态呈现错误。** 字段错误、全局读取失败、提交结果未知、业务执行未知不共用一个泛化“去设置”提示。动作必须对应实际能完成的事情。

自启整改需要特别审慎：`launchctl enable / disable` 对已有 loaded job 的实际行为，要在隔离服务中验证。不能仅凭函数改名或 mock 通过宣布“当前任务不会中断”，也不能修改 disconnect 所依赖的完整注销语义。

### 不值得做的重构

- 不更换已确定的 GPUI Kit；不再同时试多套视觉语言。
- 不重写正确的 DeviceHost / ACP 适配、回调所有权和未知结果规则。
- 不把两个具名 Harness 扩展成插件系统；不建立没有需求的 Provider 框架。
- 不为了“完整后台”加入聊天、任务编排、模型商店、资源仪表盘或权限管理页。
- 不在此次审查中假称 Windows 桌面已支持；源码共用、编译通过和目标机器验收分别说明。

## 7. 整个产品的入口与交付也要一致

- **下载 → 安装：** 公开 Swift 版与 GPUI 候选分别标识系统要求、前端和构建来源；签名、公证与本机可运行分开。当前反复替换 ad-hoc 产物引发权限重询，是分发质量问题，不能靠用户不断点允许当作完成。
- **邀请网页 → App：** 单一主要打开动作、复制链接回退、未安装指引。有效期与一次性领取说明紧邻操作。打开网页不代表接入；预览不代表已领取。
- **设备帮助：** 讲用户当前要完成的动作，引用真实按钮。管理端 CLI 与应用 SDK 指南各有入口；设备用户不落入管理员首屏。
- **Server：** 当前显式授权与重启生效适合 Developer Alpha。文档必须分清“已保存配置”和“运行中已生效”，不能承诺新增授权即时可用。此轮不扩建管理后台。
- **SDK：** 保留 `connectDock / run / status` 的简洁主路径；收据、审批回传、collect / release 的语义按任务生命周期解释，不让用户把观察超时当成执行取消。源码新能力与已发布 SDK 分开示例。
- **成功交接：** 客户端接入成功只证明设备连接；最终业务可用由调用方真实执行并验收。三类用户的“完成”不能相互代替。

## 8. 实施和验收顺序

顺序必须从真实语义到界面，避免再出现产品调整把样式带回原点。

1. 修正 P1 状态与操作契约：自启副作用、离线未知、旧连接恢复、错误死路、当前启停与解除绑定。
2. 统一状态派生与文案，再用同一结构整理概览、接入、详情、设置、菜单栏。应用自己的布局值集中管理，控件皮肤留给库。
3. 同步设备帮助、候选说明与验收命令，不改写公开旧版的事实。
4. 使用现有隔离配置和实际 GPUI 窗口完成必要检查；不新增测试框架、重型 fixture 工程或大型自动化矩阵。

验收按最短真实路径逐条留证据：

- 首次启动能理解邀请来源；邀请输入与文件导入进入同一个核对流程；不会意外提交。
- 原连接停止后，能直接启动；重新使用旧连接不会产生新身份或索要新邀请。
- 修改登录偏好不改变当前连接或执行；若暂未完成此保证，不得以普通开关交付。
- 失联或重启后的未知任务仍可见；不可维护时说明原因，不让用户先点失败才知道。
- 可选响应测试不成为接入门槛；从未测试不会被表现成错误。
- 设置始终从侧栏可见；子页返回位置一致；页面切换和刷新不清除编辑草稿或丢失必要焦点。
- 浅色、深色、最窄窗口中，主副标题、按钮、分隔线和状态说明保持同一规则；长路径可完整查看。
- 日志入口显示真实文件位置。收起 / 退出 UI 不停止独立服务，任何停止或解除绑定都只作用于选定拥有者。
- 当前安装运行的 binary 和被检查的构建一致；GPUI 构建明确单独检查。真实 Harness 执行、跨机验证、公开发行另有证据，不能由 UI 检查推导。

本轮完成的是整体审查与设计决策；未替换运行中的客户端、未修改连接、自启或执行状态，也未新增测试或发起真实模型任务。下一次实现应以以上链路和语义整体交付，不再把一次间距修正称为“整个产品完成”。
